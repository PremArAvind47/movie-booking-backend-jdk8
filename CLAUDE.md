## Concepts explained so far (simple words)
- **Llama is not code.** It is a ~2 GB file of numbers (weights). Ollama is the program that loads it and tells
  the CPU what math to run. No internet, no database, after the one-time download.
- **How an answer is made:** text, split into tokens, each token looked up as a number, numbers go through
  layers of math, model guesses the next token, add it, repeat until done.
- **Training:** the model guesses the next word over and over on huge text; wrong guesses nudge the weights.
  The training text is then thrown away; only the weights stay. Weights are like volume knobs.
- **GenAI** = generates new text word by word instead of looking up stored answers. It can hallucinate because it
  guesses from patterns and does not fact-check.
- **Tokens** = pieces of text. A model has a max (llama3.2: 131072 tokens) for question + context + answer.
- **Record** (Java 16+) = an immutable class with auto-generated constructor, getters, equals, hashCode, toString.
  This is why the project needs Java 21 and would not compile on Java 8.
- **Embedding** = text turned into a "location on a map of meaning" (768 numbers). Similar meaning means nearby.
  Vector DB stores (text, embedding) pairs and finds the closest ones to the question.
- `llama3.2` is text-only. `llama3.2-vision` handles images (planned for Part 12).

## Fine-tuning (Part 20)
General ideas (not tested here; we do NOT train anything in this project).
- **Fine-tuning** = keep training a model on your own examples, so its weights change a little. After that the model itself behaves differently.
- **RAG (what we built)** = the model stays the same; at question time we hand it the right notes (`movies.txt` chunks).

| | RAG (our project) | Fine-tuning |
|---|---|---|
| What changes | the notes we send | the model's weights |
| New or changing facts | easy: edit `movies.txt`, restart | hard: train again |
| Shows the source (chunk N) | yes | no |
| Good for | facts, documents, answers with proof | style, tone, fixed answer format, a special task |
| Needs | embeddings + vector store | training examples + a strong GPU |
| Can it make things up | less, because we check the evidence (Part 13) | yes, it can still guess |

Why not on our laptop: training needs a lot of fast GPU memory. Our laptop is CPU only with 16 GB RAM, so it is too small and too slow. People rent a GPU in the cloud, or use light methods (e.g. LoRA, which trains only a small add-on).

What training data looks like (made-up example, one line per example, formats differ by tool):
```
{"messages":[{"role":"user","content":"Seats for Batman?"},{"role":"assistant","content":"Batman has 7 free seats. Price: 200 rupees."}]}
{"messages":[{"role":"user","content":"Seats for Dune?"},{"role":"assistant","content":"Dune has 120 free seats. Price: 300 rupees."}]}
```
Rule of thumb: try a good prompt first, then RAG, then fine-tuning last. For our movie project RAG is the right tool, because the movie facts change.

## Debugging checklist (Part 23)
Method (5 steps):
1. Get the request id: it is in the response header `X-Request-Id`, or in `[...]` on every console line of that request (also in the `logs` folder).
2. Find all lines with that id and read them from top to bottom.
3. Find the LAST line that looks right. The problem is in the next step of the path (filter > guard > cache > search > model > grounding > answer).
4. Use the table below.
5. Change ONE thing, ask again, check the same lines.

| Symptom | Log line to look for | What it means | What to try |
|---|---|---|---|
| "I don't know. The file has no information about that." very fast (ms) | `TIMING search: N ms, 0 chunk(s) found` | no chunk passed the minimum score (`rag.min-score=0.5`) | ask with words closer to the file; check `movies.txt` has the fact; lower `rag.min-score` a little |
| "I don't have enough information to answer that." | `Answer rejected, the model said not found or gave no evidence` | the model said found=false or gave no evidence | read the `RAG chunk score=... text=...` lines: is the answer in those chunks? If not: search problem (top-K, chunking). If yes: model too weak |
| same message | `Answer rejected, evidence not found in the chunks` | the model wrote an evidence sentence that is NOT inside the chunks (made up or reworded) | compare the evidence in the log with the chunk text |
| the answer is just one sentence from the file | `The model left the answer empty, using the evidence sentence instead` | the model sent an empty answer but a correct evidence | normal, this is the fix from Part 15 |
| wrong answer, wrong movie | `RAG chunk score=` lines show other movies | search found the wrong chunks | chunking, top-K, wording, embedding model |
| very slow | `TIMING search` vs `TIMING model` | usually the model is ~98% of the time; first call ~66 s is a cold load | wait for the warm run, smaller model, cache, `/ai/stream` |
| instant answer, no TIMING lines | `CACHE hit: answer taken from the cache` | a saved answer was returned | new wording, or restart the app (the cache is lost on restart) |
| 400 "This text is not allowed." | `Blocked a possible prompt injection: ...` | InputGuard (trick phrase, empty, or more than 300 characters) | change the text |
| 503 "The AI model is not available. Is Ollama running?" | `The AI model is not reachable: ...` | Ollama is stopped, or `OLLAMA_URL` is wrong | start Ollama; `curl http://localhost:11434/api/tags` |
| 504 "took too long" | `The AI model did not answer in time: ...` | read timeout (`HTTP_READ_TIMEOUT`, default 180 s) | cold or too big a model; raise the timeout only if needed |
| a request hangs for minutes | many `Retry error` WARN lines | Spring AI retries failed calls (we set 2 attempts, default is 10) | check `spring.ai.retry.max-attempts` |
| a tool was not called, or got a wrong argument | `TOOL ... called with ...` lines (or none) | the model chose wrong or ignored the tool; llama3.2 (3B) did this, qwen2.5:7b worked | stronger model, clearer `@Tool` / `@ToolParam` descriptions |
| guest sees no customer data | `ACCESS DENIED: role=GUEST ...` | works as designed (ADMIN only) | send header `X-Role: ADMIN` |
| app does not start, long error with `Connection refused ... /api/embed` | no `Loaded 4 chunks` line | Ollama was not running at startup | start Ollama first, then the app |
| `COST: the model did not report token counts` | that line | Ollama did not send token counts | harmless |
| `/ai/evaluate` score drops | `EVAL [group] name -> FAIL` lines | the quiz found a weak spot | find the matching symptom above and read its log lines |

Real cases we solved with this method: (1) black hole false rejection: logs showed `found=true, answer=<empty>, evidence=<right sentence>` -> prompt fix + use the evidence as answer; (2) llama3.2 called `getFreeSeats` with `movieName=getMovieList` -> switched to qwen2.5:7b; (3) a hung test took minutes -> found Spring AI retries -> `max-attempts=2`; (4) `/ai/stream` gave a long 500 when Ollama was down -> a different exception class -> handler catches both.
Not covered: a model that is not pulled (Ollama answers 404; would show as a 500 and `AI call failed ...` in the console); a stream that breaks after words already started.
